Documento de Decisiones de Modelado - Laboratorio 3
1. Normalización y CatálogosPara estructurar los datos del sistema, decidimos separar la información descriptiva que se repite en tablas de catálogo como Category, Brand y Unit. Esto evita que los usuarios escriban variaciones de la misma palabra (como "Kg" o "Kilo") en la tabla principal de productos, manteniendo la base de datos limpia, normalizada y optimizada para las búsquedas y los filtros.  
2. Tabla inventory_movements Una de las decisiones más importantes fue cómo manejar las entradas y salidas de bodega de forma segura. En la tabla inventory_movements implementamos una relación polimórfica. Con los campos dinámicos movementable_type y movementable_id, un movimiento de inventario se puede conectar exactamente con un ítem de venta (Sale_Items) o un ítem de compra (Purchase_Items). Esta relación la manejamos de 1 a 1 para garantizar la integridad referencial y asegurar que cada alteración del stock tenga un único comprobante de respaldo. 
3. Pagos asociados a las Ventas (POS)Ajustamos el modelo transaccional para que los pagos (Payments) se conecten directamente con las ventas (Sale) y no con los pedidos web (Order). Esto tiene sentido práctico para la ferretería: si un cliente llega a la tienda física, el cajero genera la venta y se le cobra ahí mismo. Al hacer esta relación de uno a muchos (1:N), el sistema permite que un cliente pague una misma factura usando métodos mixtos (por ejemplo, mitad en efectivo y mitad con tarjeta). 
4. Convenciones de Laravel (Eloquent)Decidimos ajustar los nombres de todas las llaves primarias y foráneas al estándar estricto de Laravel (snake_case, usando por ejemplo category_id en lugar de id_Category). Esto nos facilitó mucho la configuración de las relaciones en los modelos de Eloquent y solucionó problemas de compatibilidad de llaves foráneas que teníamos con SQLite. También aplicamos borrado lógico (Soft Deletes) a la tabla Product para que, si se discontinúa un artículo, no se rompa el historial de las facturas antiguas.
5. Atributos clave para el negocioAñadimos campos adicionales específicos a la entidad principal pensando en los requisitos de los diferentes módulos:  barcode: Para permitir el uso de pistolas de escaneo en el punto de venta (POS).tax_rate: Para calcular el IVA de forma dinámica en cada ítem, permitiendo vender productos con impuestos variados o exentos.weight: Para poder calcular automáticamente los costos de flete o transporte cuando se implemente el E-commerce y el carrito de compras.
